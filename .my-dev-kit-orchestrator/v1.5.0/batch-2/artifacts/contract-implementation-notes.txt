===============================================================================

  npx @dailephd/my-dev-kit@latest lookup --index .my-dev-kit \
    --node "symbol:src/indexing/manifestTypes.ts#IndexAnalyzerArtifactRef" --depth 1 --json

    --node "symbol:src/indexing/manifestTypes.ts#IndexAnalyzerArtifactRef" --depth 1 --direction both --json

Both commands returned the node object with `semanticRoles` and `artifactRefs`
present byte-for-byte identical to the raw code-graph.json node (no

directly from `CodeGraph.nodes` entries with no field allowlist/denylist.

slice include `semanticRoles` and `artifactRefs` from `code-graph.json` when
present." docs/ARCHITECTURE.md line 30 corroborates: "slice command -> Graph
slicing, preserves semantic metadata on nodes."

Resolution: NO slice-command code change is needed in Batch 2. Since
`classificationRoles`/`classificationRefs` are added as new optional fields
on the same `CodeGraphNode` type using the same shape/pattern as
`semanticRoles`/`artifactRefs`, they will be preserved through slice output
automatically once they exist on the node object written to code-graph.json.
Batch 2's scope is therefore exactly "make the compact fields exist on
CodeGraphNode/GraphSymbolRecord" - it does not need a slice.ts change, and
does not implement Batch 3's command-output-formatting scope (e.g.
summarizing classification in slice's printed output) or produce a
dedicated slice test beyond the existing serialization test in
tests/classification/applyClassificationToCodeGraph.spec.ts (TST-041) plus
one thin integration check in classificationArtifact.spec.ts that reads
code-graph.json and confirms the fields exist after an index run.

4. Static patterns for command-handler, analyzer, and validator (resolved -
   concrete, evidence-grounded definitions; validator no longer undefined)
===============================================================================

command-handler (file-level):
  - Directory: file path starts with `src/commands/`
  - Naming: filename matches `*Command.ts` (case-sensitive suffix)
  - Export evidence: file exports a function matching `/^register[A-Z]\w*Command$/`
    taking a `Command` (commander) parameter - confirmed present in ALL 7
    files under src/commands/ that end in "Command.ts" (registerViewCommand,
    registerLookupCommand, registerSourceCommand, registerIndexCommand,
    registerSearchCommand, registerSliceCommand, registerDataModelCommand).
  - Negative control confirmed: src/commands/parseUtils.ts (no "Command"
    filename suffix, no register* export) correctly does NOT match - proves
    the pattern's precision rather than being directory-only.
  - Confidence: 'certain' when directory + filename + register*Command export
    all match; 'likely' when directory + filename match but the export check
    cannot run (e.g. classifying a file in isolation without full-project
    symbol data); 'possible' when only the directory matches (e.g. a new file
    under src/commands/ with an unconventional name).

analyzer (file-level):
  - Directory: file path starts with one of `src/semantics/`, `src/data-model/`,
    `src/frontend/`, `src/frontend-reachability/` (excludes that directory's
    own `types.ts`/`*Types.ts`/`index.ts`, which are type-definition/barrel
    files, not analyzer logic).
  - Naming: filename contains `Analyzer` (frontendAnalyzer.ts,
    runFrontendReachabilityAnalyzer.ts) OR starts with `build` (
    buildDataModelArtifact.ts, buildDataModelFromIndex.ts, buildDataModelGraph.ts,
    buildSemanticRolesFromDataModel.ts, buildReachabilityLookupResult.ts,
    buildReachabilitySearchResult.ts, buildReachabilitySliceResult.ts,
    buildReachabilitySourceResult.ts) OR starts with `apply` (
    applySemanticRolesToCodeGraph.ts, applySemanticRolesToSymbolIndex.ts) OR
    starts with `run` and contains `Analyzer` (covered above) - all 4
    directories' non-types/non-index files were enumerated via Glob and every
    file matches one of these four naming shapes.
  - Confidence: 'likely' when directory + naming both match (this is the
    common case observed in this codebase); 'possible' when only the
    directory matches (e.g. a helper file added later with a naming
    convention not yet covered); never 'certain' purely from naming, since
    file purpose can't be fully confirmed without symbol-level export
    inspection, which classification's conservative file-level pass does not
    perform.

validator (file-level) - previously undefined, now concretely defined:
  - No file in my-dev-kit's OWN codebase is named "validator"/"validation" at
    the src/commands or src/semantics/data-model/frontend* directory level
    (confirmed by Glob across those directories - no exclusion needed there).
    However, concrete grounding DOES exist elsewhere in this same repo:
    `src/io/validation.ts` is a real file, literally named "validation.ts",
    with a doc comment "Lightweight validation helpers for config loading and
    generator scripts" and exports `requireString`, `requireArray`,
    `requireNonEmptyArray`, `requireEnum`, `assert` - all guard-style
    functions that throw on invalid input and return the validated value.
    This is directly-observed evidence for the pattern definition below (it
    grounds the pattern in a real instance, even though my-dev-kit's own
    src/commands and analyzer directories don't separately contain a
    "validator"-named file - classification targets ANY indexed project, not
    only my-dev-kit's own source).
  - Naming: filename matches `/^valid(ate|ation|ator)/i` (e.g. validation.ts,
    validator.ts, validate.ts, Validator.ts) OR a path segment equals
    `validators` (directory convention, e.g. `src/validators/userValidator.ts`).
  - Export evidence: file's exported symbols are predominantly functions
    matching `/^(validate|require|assert|is[A-Z]\w*Valid|check[A-Z])/` naming
    AND those functions either throw on invalid input or return a
    boolean/narrowed type (confirmed shape of src/io/validation.ts's
    `requireString`/`requireArray`/`requireEnum`/`assert`).
  - Confidence: 'likely' when BOTH filename and export-shape evidence align
    (as in src/io/validation.ts); 'possible' when only the filename/directory
    matches without corroborating export evidence (avoids overclaiming from
    name alone, consistent with BEH-011's conservative-evidence requirement);
    never 'certain' for validator specifically, since a name match alone is
    not strong enough evidence per the conservative rule, and export-shape
    matching is itself a heuristic rather than a guaranteed-correct signal -
    this keeps validator's ceiling one tier more conservative than
    command-handler's, reflecting that "Command" suffix + register*Command
    export is a much stronger, more mechanical signal than "looks like a
    guard function."
  - This resolves the readiness report's explicit blocking concern: the
    validator pattern is no longer undefined. It is grounded in a real file
    in this repository (src/io/validation.ts) rather than invented from
    nothing, satisfying the conservative/evidence-backed requirement.

7. Correction to Batch 1's BEH-020 reuse-by-name assumption (found during
   Batch 2 implementation, not a contract conflict - a mechanical detail)
===============================================================================

`grep -rn "role: '" src/ --include="*.ts"` across the entire codebase finds
exactly ONE place any `SemanticRole.role` value is ever assigned:
`src/semantics/buildSemanticRolesFromDataModel.ts:29: role: 'data-entity'`.
No analyzer anywhere in this codebase ever sets `role` to `canonical-type`,
`database-model`, `view-model`, `ui-only-state`, `client-component`,
`server-component`, `route-handler`, `persistence-adapter`, or
`test-fixture` - despite these all being valid `SemanticRoleName` union
members. The category distinction that DOES exist lives in `subtype`
(`entityKindToSubtype`: `'canonical-model' -> 'canonical-type'`,
`'schema-model' -> 'schema-model'`, `'view-model' -> 'view-model'`, else
`'unknown'`).

This does not conflict with classification-contract.txt or behavior-model.txt
(BEH-020 says "reuse the same category name," it does not specify which
field on `SemanticRole` carries that name) - it is a mechanical detail Batch
1's architecture-context retrieval did not drill into (it confirmed the
`SemanticRoleName` union's members, not which producer actually populates
`role` vs. `subtype` in practice). Resolution: `classifySymbols.ts`'s
existing-role lookup checks BOTH `existingRole.role` and
`existingRole.subtype` for a v1.5-category match, reusing whichever field
carries the matching name verbatim (in practice, `subtype` for
data-model-sourced symbols today). This honors BEH-020's naming-consistency
intent exactly; it is a one-line implementation detail, not a deviation from
the contract, and is called out explicitly in
batch-2-implementation-report.txt's "deviations from Batch 1 contract"
section for transparency.
