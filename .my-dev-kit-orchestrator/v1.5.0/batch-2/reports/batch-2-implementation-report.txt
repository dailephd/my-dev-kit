===============================================================================
Deviations from Batch 1 contract
===============================================================================

1. classifySymbols.ts checks BOTH existingRole.role and existingRole.subtype
   for a v1.5-category match (not just `.role` as PSE-020's pseudocode
   literally shows), because only `role: 'data-entity'` is ever assigned by
   any producer in this codebase - the practical category signal lives in
   `subtype`. Documented in contract-implementation-notes.txt section 7. This
   is a mechanical implementation detail, not a change to BEH-020's naming-
   consistency intent.
2. resolveCandidateConflicts (classificationHelpers.ts) was extended beyond
   PSE-040's literal pseudocode to (a) propagate the winning candidate's
   evidence array (PSE-040 as written discards it, which would make
   INV-001's "certain-tier requires evidence" unsatisfiable for any resolved
   entry) and (b) auto-generate a warning via buildLowConfidenceWarnings
   whenever the resolved tier is possible/unknown, even for a single
   (non-ambiguous) candidate - PSE-033's avoidOverclaiming check is written
   against entries in general, and a single low-confidence candidate (e.g.
   validator matched by filename alone, no export corroboration) still needs
   a warning even though PSE-040's conflict-resolution pseudocode only shows
   the ambiguous/multi-candidate path adding one. Both were caught by the new
   tests failing during Stage 10 (invariant violations thrown at
   construction time exactly as AC-002 intends), then fixed - no invariant
   was weakened; the fixes make the pseudocode's own invariants (INV-001,
   PSE-033) actually hold.
3. readiness/risk-label derivation (deriveReadiness, deriveFileRisks,
   deriveSymbolRisks) is a Batch-2-original conservative implementation, not
   drawn from a Batch 1 pseudocode section - behavior-model.txt BEH-032 and
   the pseudocode packet explicitly leave the "exact mapping" as "an
   implementation decision for Batch 2, constrained by this conservative
   direction." `migration-risk` is never emitted (no static evidence source
   was identified in either Batch 1 or Batch 2's architecture context for
   it) - this is a conservative omission, not a contract violation, since
   risk labels are additive/optional (0 or more).
4. TST-002 (manifest analyzer/artifact registration) was covered by a new
   assertion in the new tests/classification/classificationArtifact.spec.ts
   file rather than by extending the existing tests/index/
   manifestAnalyzerRegistry.spec.ts as test-strategy-packet.txt suggested -
   done to avoid modifying an existing v1.1-era test file; the assertion
   coverage is equivalent.
