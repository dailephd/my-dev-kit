===============================================================================
Shared metadata resolver/loader plan
===============================================================================

New file: src/classification/resolveClassificationForCommands.ts (extends
Batch 2's src/classification/ module - not a new/parallel architecture):
- resolveClassificationArtifactPath(manifest, indexDir): reads
  manifest.analyzers to find id==='classification', returns its first
  artifact's resolved absolute path (with the same escape-path safety check
  pattern already used in readIndexManifest.ts's resolveArtifactPath), or
  null if the analyzer entry/artifact/file is absent.
- loadClassificationArtifact(indexDir, manifest): reads and JSON-parses the
  file, returns null on any failure (missing analyzer entry, missing file,
  malformed JSON) - never throws, matching INV-004's graceful-degradation
  requirement and this batch's stop condition ("missing classification
  artifact causes command crashes").
- findClassificationEntryByTargetId(artifact, targetId): linear find by
  entry.targetId (classification.json is small/index-scoped, not worth a Map
  for the expected entry counts).
- buildClassificationCommandSummary(entry): compact projection - returns
  {classifications, editGuidance, readiness, risks, uncertainty, evidenceRefs,
  artifactRefs, warnings} (evidenceRefs is entry.evidence[].sourceLocation,
  deduplicated - a compact ref list, NOT the full evidence objects with
  staticPattern/reason text, keeping command output bounded per the task's
  "avoid loading unrelated large artifacts" / "do not duplicate the whole
  detailed artifact" constraints).

search does NOT call this resolver at all - its compact fields
(classificationRoles/classificationRefs) already live directly on the
matched CodeGraphNode/SymbolDefinition, exactly like semanticRoles/
artifactRefs today; no classification.json read is needed for search.

lookup calls this resolver ONLY when a new --resolve-classification flag is
passed (opt-in, matching the contract's "plus an option to resolve
classificationRefs into full ClassificationEntry detail ... on request" -
lookup's on-request resolution returns the FULL ClassificationEntry, not the
summary, since the contract explicitly says "full ClassificationEntry
detail").

source calls this resolver unconditionally but tolerates a null result
silently - it attaches the compact buildClassificationCommandSummary() (not
the full entry) inline as a new optional `classificationSummary` field,
satisfying "source should include warnings for generated-file risk,
wrong-layer risk, or uncertainty ... if supported by the classification
artifact" without turning source into a second detailed-artifact viewer.

===============================================================================
Output compatibility plan
===============================================================================

All new fields are additive and optional (`?`), appended after existing
fields in each type, mirroring exactly how semanticRoles/artifactRefs/
evidenceRefs were added in v1.1/v1.2. No existing field is renamed, removed,
or repurposed. JSON output remains valid; plain/numbered text output for
source gets one new optional line only when a classification summary exists
(risks/edit-guidance), otherwise output is byte-identical to pre-Batch-3.
Search ranking (rankSearchResults.ts) is NOT modified - classification
fields are surfaced on result items exactly like semanticRoles today
(informational only, not search-ranked) unless testing reveals the contract
requires classification-term matching (see Stage 5 below); this keeps
ranking behavior deterministic and unchanged from v1.1-v1.4.
