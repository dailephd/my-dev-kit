Mapping from Batch 3 command behavior to tests
===============================================================================

- search matches classification role/edit-guidance as searchable fields ->
  searchIntegration.spec.ts "matches classification role/edit-guidance terms
  as searchable fields" (verified live via CLI smoke with query "canonical"
  in addition to the unit-style test).
- search/lookup/slice/source remain stable when classification.json is
  missing -> covered per-command in each *Integration.spec.ts file AND
  comprehensively in missingClassificationArtifact.spec.ts (all four
  commands against the same missing-artifact fixture, plus a check that
  manifest.json can still reference the (now-deleted) classification
  artifact without causing a crash - the "stale registry" scenario).
- lookup's opt-in --resolve-classification flag -> lookupIntegration.spec.ts
  (present when requested, absent when not requested, null when the
  artifact is missing).
- slice does not duplicate the full detailed classification artifact ->
  sliceIntegration.spec.ts "does not duplicate the entire detailed
  classification artifact in slice output" (asserts the compact
  ClassificationRoleRef shape only - no evidence/sourceRefs/reason fields).
- slice determinism -> sliceIntegration.spec.ts "slice output remains
  deterministic across repeated runs".
- source's line-range mode (no symbol target) correctly has no classification
  fields (not every source retrieval mode has a symbol/file classification
  target) -> sourceIntegration.spec.ts "line-range retrieval still works and
  classification fields are simply absent".

===============================================================================
Uncovered test responsibilities and reasons
===============================================================================

- The other three getSourceSlice call sites in sourceCommand.ts (exact-match,
  continue-from, node-continue) were intentionally NOT extended with
  classification metadata in this batch (see implementation report "risks"
  section) because they do not carry semanticRoles/artifactRefs today either
  - extending only these three modes for classification while every other
  mode already lacks semantic metadata would be an inconsistent, scope-
  creeping change. No test asserts classification presence/absence for these
  three modes since their behavior is intentionally unchanged from pre-
  Batch-3 (already implicitly covered by tests/source/exactMatch.spec.ts,
  tests/source/sourceContinuation.spec.ts, etc. continuing to pass unmodified
  in the full suite run).
- rankSearchResults.ts's ranking ALGORITHM itself has no dedicated new test
  in this batch - the existing generic-scorer test coverage (tests/search/
  searchIndex.spec.ts, searchCommand.spec.ts) already exercises it, and this
  batch adds candidate fields (classificationRole/classificationEditGuidance)
  through the exact same generic mechanism already covered by those tests;
  a new field type does not need a new ranking-algorithm test since ranking
  is field-name-agnostic (confirmed by reading rankSearchResults.ts - no
  hardcoded field-name branches).
