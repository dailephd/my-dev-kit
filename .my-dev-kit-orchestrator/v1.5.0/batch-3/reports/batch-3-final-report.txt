===============================================================================
Search integration result
===============================================================================

PASS. search results for classified targets include `classificationRoles`/
`classificationRefs` (the compact projection: role + editGuidance +
readiness + uncertainty), sourced directly from the matched node/symbol -
zero classification.json reads needed for search. Classification role and
edit-guidance values are also searchable terms (query "canonical" correctly
matched all three canonical-type-classified symbols in the live CLI smoke).
Ranking algorithm (rankSearchResults.ts) is unmodified - it is field-name-
agnostic, so no ranking-specific change was needed. Existing semanticRoles/
artifactRefs search behavior is unchanged (verified by regression tests and
the unmodified full suite). Search remains stable (valid JSON, exit 0) when
classification.json is missing.

===============================================================================
Lookup integration result
===============================================================================

PASS. `classificationRoles`/`classificationRefs` appear both at the top
level of lookup's result and nested inside `node` (mirroring exactly how
semanticRoles/artifactRefs already appear in both places). New opt-in
`--resolve-classification` flag resolves the full `ClassificationEntry` from
classification.json only when requested (per classification-contract.txt
section 8's "on request" wording) - absent when not requested, `null` (not
an error) when classification.json is missing even if requested. Existing
semanticRoles/artifactRefs/evidenceRefs lookup behavior is unchanged.

===============================================================================
Slice integration result
===============================================================================

PASS - with zero code changes. `classificationRoles`/`classificationRefs`
already appear on classified nodes in slice output because slice performs a
raw `CodeGraphNode` passthrough with no field allowlist (confirmed both via
a live CLI smoke run and a dedicated regression test). The full detailed
classification.json is never duplicated into slice output - only the
compact `ClassificationRoleRef` projection appears, matching the same
compactness already established for semanticRoles/artifactRefs. Slice output
remains deterministic across repeated runs (dedicated test). Existing
semantic metadata preservation is unchanged.

===============================================================================
Source integration result
===============================================================================

PASS. `classificationRoles`/`classificationRefs` are threaded through the
`--node` and `--file`/`--symbol` (and the equivalent `symbol-continue`)
retrieval paths, mirroring exactly how `semanticRoles`/`artifactRefs`/
`evidenceRefs` already flow through those same two `getSourceSlice` call
sites. A new compact `classificationSummary` field (editGuidance, readiness,
risks, uncertainty, warnings, deduplicated evidenceRefs - NOT the full
per-evidence text/reason objects) is resolved via the shared
`resolveClassificationForCommands` module and attached when available. The
default plain-console output prints one new concise line
("Classification edit guidance: ...") only when a summary exists, mirroring
the existing warnings-line pattern; JSON output carries the field in a
stable location; the explicit `numbered`/`plain` `--format` renderers are
intentionally left unchanged (they don't surface semantic warnings either
today, so adding classification notes only there would be new, inconsistent
behavior beyond mirroring the existing pattern). Line-range retrieval
(no symbol/file classification target) correctly has the fields absent, not
null-shaped placeholders. v1.4 source continuation/expansion behavior
(tests/source/sourceContinuation.spec.ts, localDependencyExpansion.spec.ts)
is unaffected - confirmed unmodified passing in the full suite, and by
construction, since sourceBundle.ts/renderSourceBundle.ts and the three other
getSourceSlice call sites (exact-match, continue-from, node-continue) were
not touched.

===============================================================================
Missing-artifact fallback result
===============================================================================

PASS across all four commands, verified by both automated tests
(missingClassificationArtifact.spec.ts, 6 tests) and live CLI smoke (search/
lookup/source against a real index with classification.json deleted). No
command crashes; all JSON output remains valid; `lookup --resolve-
classification` returns `classificationDetail: null`; `source` returns
`classificationSummary: null`; compact `classificationRoles`/
`classificationRefs` fields (which live on the node/symbol object itself,
not in classification.json) correctly remain present even when the detailed
artifact is absent, since they were written to symbol-index.json/
code-graph.json at index time by Batch 2's producer.
