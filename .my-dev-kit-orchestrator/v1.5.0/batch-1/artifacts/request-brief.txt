Artifact: RequestBrief
Batch: v1.5.0 Batch 1 - Classification Planning and Contracts
Workflow mode: feature
Workflow depth: Depth 2 (cross-cutting implementation, per revised graph-guided orchestrated workflow)

Original request:
v1.5.0 adds conservative static schema/layer classification across files, symbols,
types, and artifacts, then surfaces classification, edit guidance, readiness, risk,
evidence, and uncertainty through existing retrieval workflows without creating a
parallel retrieval system. v1.5.0 should help coding agents avoid editing the wrong
layer by classifying project files, symbols, types, and artifacts by their role, and
by exposing conservative edit guidance, readiness, risk, evidence, and uncertainty
through existing retrieval workflows.

Requested change:
Produce the planning and contract foundation for v1.5.0 classification:
architecture context retrieval, a behavior model, a classification artifact and
metadata contract, a classifier pseudocode packet, and a test strategy packet.
This batch does not implement production code, does not write tests, and does not
touch docs, publishing, or release workflows.

Target area:
- Project: my-dev-kit (indexing/analysis CLI)
- Components likely affected in later batches: semantic analyzers, manifest
  registry, symbol-index / code-graph enrichment, search/lookup/slice/source
  command output
- Workflow surface: retrieval workflow (search, lookup, slice, source) plus the
  index/manifest pipeline that produces artifacts consumed by those commands
- This batch's own surface: planning artifacts only, under
  .my-dev-kit-orchestrator/v1.5.0/batch-1/

User-visible or external behavior:
- Coding agents using search/lookup/slice/source should see classification labels,
  edit guidance, readiness, risk, evidence, and uncertainty for files, symbols,
  types, and artifacts they are inspecting.
- This should reduce wrong-layer edits (e.g. editing a generated file, a database
  model instead of a view-model, or a read-only reference file).
- No change to existing command behavior when classification data is absent
  (graceful degradation).
- This batch itself has no user-visible behavior change; it only produces planning
  artifacts.

Constraints:
- Local-first: no LLM calls, no network calls from my-dev-kit itself, no database
  connections, no source file edits.
- Classification must be static and conservative; must not claim runtime behavior.
- Must not create a parallel retrieval system alongside search/lookup/slice/source.
- Must preserve v1.1-v1.4 behavior (data-model semantics, frontend semantics,
  route/storage/reachability if present, source continuation/expansion).
- Must use latest published @dailephd/my-dev-kit and
  @dailephd/my-dev-kit-orchestrator packages for index/search/orchestrator
  commands, not local unpublished code.
- Do not modify package version unless an established versioning workflow requires
  a v1.5.0 development version (not confirmed in this batch; treated as no-op
  unless architecture context shows otherwise).
- No production code, no test code, no docs updates, no publishing, no release
  branch work in this batch.

Non-goals:
- v1.6 planner packets / context capsules
- v1.7 retrieval benchmarks
- v1.8 scalability work
- v1.9 language/framework expansion
- v2.0 plugin architecture
- LLM semantic similarity, runtime React visibility proof, browser execution,
  database introspection, schema v2 migration
- Any pre-release/publish/release-branch workflow execution

Success criteria:
- Architecture context packet answers all required questions and ends with an
  explicit context adequacy statement.
- Behavior model defines externally visible behavior, internal behavior,
  classification categories, edit guidance, readiness/risk, evidence, uncertainty,
  behavior to preserve, and non-goals without deciding implementation.
- Classification contract defines artifact name/schema, target model, entry shape,
  compact metadata shape, evidence model, uncertainty model, backward
  compatibility, and future command integration contract.
- Pseudocode packet is implementation-neutral (no production TypeScript) and
  covers pipeline, file classification, symbol/type classification, evidence and
  uncertainty helpers, integration points, and acceptance criteria.
- Test strategy packet derives test responsibilities from the above artifacts
  without writing test code.
- Verification report captures git/npm/build/typecheck validation relevant to a
  planning batch.
- Final report summarizes the batch and recommends Batch 2.

Ambiguity or missing information:
