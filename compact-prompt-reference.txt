Graph-Guided Symbol Retrieval compact prompt reference

Tool identity

my-dev-kit is a local CLI for indexing codebases and retrieving bounded code context.

This reference is for pre-release work from inside the my-dev-kit project folder.

Use local project commands:

npm run build
node dist/cli.js <command>

Do not switch these templates to npm package commands until the release is published.

Main commands

Core commands:
- index
- search
- lookup
- slice
- source
- view

Semantic inspection command, when implemented:
- data-model

Core artifacts

Structural artifacts:
- manifest.json
- symbol-index.json
- code-graph.json
- call-graph.json, when --call-graph is requested and produced
- graph slice JSON, when slice is run
- DOT/SVG/PNG graph output, when view is run

Semantic artifacts, when generated:
- data-model.json
- data-model-graph.json
- model-view-lineage.json

Semantic metadata, when present:
- semanticRoles
- artifactRefs
- evidenceRefs
- analyzer status in manifest.json

Artifact directory rule

Use one stable artifact directory for normal work:

.my-dev-kit

The index represents the current state of the project. Re-run index to refresh the same artifact directory unless the task explicitly needs a separate audit, comparison, or snapshot output.

Do not create a new index folder for every run.

Use custom --out only when there is a clear reason, such as:
- indexing a monorepo subproject separately
- comparing old and new outputs
- creating a planning/audit index
- debugging a specific source root

Workflow principle

Do not start by reading whole files.
Do not guess file responsibilities from the repo tree alone.
Do not open broad directories or unrelated files.

Use this order:

1. Use search to narrow candidate nodes.
2. Use lookup on candidate node IDs.
3. Use slice around the strongest node.
4. Use source on exact symbol IDs when possible.
5. Use line-range source only as fallback.
6. Use data-model inspection only when the task involves entities, fields, model semantics, or model-to-view lineage.

Step 1: Build the CLI from local source

Run from inside the my-dev-kit project folder:

npm run build

Step 2: Index the target repo

Basic TypeScript/JavaScript indexing:

node dist/cli.js index --root <target-repo-root> --src <source-root> --out <target-repo-root>/.my-dev-kit --json

With multiple source roots:

node dist/cli.js index --root <target-repo-root> --src <source-root-1> --src <source-root-2> --out <target-repo-root>/.my-dev-kit --json

With call graph:

node dist/cli.js index --root <target-repo-root> --src <source-root> --out <target-repo-root>/.my-dev-kit --call-graph --json

Python indexing:

node dist/cli.js index --root <target-repo-root> --src <source-root> --language python --out <target-repo-root>/.my-dev-kit --json

Index command flags:
- --root <path>: target repository root
- --src <path>: source root, repeatable
- --language <typescript|javascript|python>: language hint when needed
- --out <dir>: output artifact directory
- --call-graph: also build call graph when supported
- --json: print machine-readable result

Index output expectations

The index command produces or refreshes managed artifacts in the selected output directory.

Expected structural artifacts:
- manifest.json
- symbol-index.json
- code-graph.json
- call-graph.json, when requested and produced

Expected semantic artifacts, when implemented and generated by the current index configuration:
- data-model.json
- data-model-graph.json
- model-view-lineage.json

manifest.json is the source of truth for which artifacts are current. Do not assume that a stale file is current just because it exists in the artifact directory.

Step 3: Search for candidate nodes

Search task-specific terms:

node dist/cli.js search --index <index-dir> --query "<query term>" --limit 20 --json

Search command flags:
- --index <dir>: index artifact directory
- --query <text>: local deterministic search query
- --limit <n>: number of results
- --json: print machine-readable result

Query term rules:
- Use concrete words likely to appear in code.
- Prefer symbol names, file names, command names, types, edge labels, and behavior terms.
- Use semantic role terms when relevant and implemented, such as data-entity, view-model, canonical-type, artifact-type, route-handler, react-component, or test-block.
- Run several small searches instead of one vague search.

Good query examples:
- "buildDotGraph"
- "source command"
- "GraphViewResult"
- "edge label"
- "language registry"
- "python adapter"
- "resolve source target"
- "path traversal"
- "view command"
- "data-entity"
- "semanticRoles"
- "artifactRefs"
- "model-view lineage"

Bad query examples:
- "make this better"
- "visual stuff"
- "fix architecture"
- "understand project"

Step 4: Filter search results

Select candidate nodes using these rules:
- Prefer kind=symbol over kind=file when the task targets a function, class, type, command handler, or exported constant.
- Prefer paths inside the likely subsystem.
- Prefer match reasons on symbolName, path, export, nodeId, label, semanticRoles, or artifactRefs.
- Deprioritize import-only matches or generic edge endpoint matches.
- Reject unrelated subsystem paths unless lookup proves relevance.
- If search returns only a file result, search again using the filename stem or likely exported symbol name.

Useful result fields:
- id or nodeId: exact graph node ID
- kind: symbol or file
- path: source path
- label: display label
- score: deterministic ranking value, not probability
- matchReasons: why the result matched
- semanticRoles: compact application-level classifications, when present
- artifactRefs: references to detailed semantic artifacts, when present
- evidenceRefs: source evidence references, when present

Step 5: Lookup candidate nodes

Run lookup on actual selected IDs from search:

node dist/cli.js lookup --index <index-dir> --node "<selected-node-id>" --depth 1 --json

Lookup command flags:
- --index <dir>: index artifact directory
- --node <node-id>: exact node ID
- --depth <0-3>: relationship depth
- --json: print machine-readable result

Use lookup to answer:
- What file defines this symbol?
- What symbols are defined by this file?
- What imports or depends on this node?
- What does this node call or connect to?
- Which neighboring files or tests are relevant?
- What semantic roles does this symbol have, if semantic metadata is present?
- Which detailed artifacts does this symbol reference, if artifactRefs are present?
- Which source evidence supports the semantic role, if evidenceRefs are present?

Step 6: Slice around the strongest node

Choose the strongest node based on:
- direct relevance to the requested change
- symbol-level specificity
- subsystem path match
- useful incoming and outgoing relationships
- test/type/command relationships revealed by lookup
- semantic role relevance when semanticRoles are present

Then create a bounded slice:

node dist/cli.js slice --index <index-dir> --node "<strongest-node-id>" --depth 2 --direction both --out <index-dir>/<task-name>-slice.json --json

Slice command flags:
- --index <dir>: index artifact directory
- --node <node-id>: exact focus node ID
- --depth <0-3>: graph traversal depth
- --direction <both|incoming|outgoing>: traversal direction
- --out <path>: optional output file
- --json: print machine-readable result

Depth guidance:
- depth 0: only the focus node
- depth 1: immediate relationships
- depth 2: usually best for implementation planning
- depth 3: use only when the subsystem is still unclear

Semantic note:
- Slice should preserve compact semantic metadata when present.
- Do not assume slice traverses data-model-graph.json or model-view-lineage.json unless that behavior is explicitly implemented.

Step 7: Retrieve source by exact symbol first

Preferred source retrieval:

node dist/cli.js source --index <index-dir> --node "<selected-symbol-node-id>" --max-lines 160 --format numbered

Source by file plus symbol:

node dist/cli.js source --index <index-dir> --file "<selected-file-path>" --symbol "<selected-symbol-name>" --max-lines 160 --format numbered

Source command symbol flags:
- --index <dir>: index artifact directory
- --node <symbol-node-id>: exact symbol node
- --file <path>: source file path
- --symbol <name>: symbol name inside file
- --max-lines <n>: cap returned lines
- --format <json|plain|numbered>: output format
- --out <path>: write rendered output to file
- --json: compatibility machine-readable output when supported

Use symbol retrieval for:
- functions
- classes
- types
- command registration functions
- exported constants
- language adapters
- parser helpers
- graph builders
- semantic analyzers
- artifact builders
- manifest readers/writers

Step 8: Use line-range source only as fallback

Fallback form:

node dist/cli.js source --index <index-dir> --file "<selected-file-path>" --start <start-line> --end <end-line> --max-lines <cap> --format numbered

Line-range source flags:
- --file <path>: source file
- --start <n>: starting line
- --end <n>: ending line
- --max-lines <n>: maximum allowed returned lines
- --format <json|plain|numbered>: output format
- --out <path>: write output to file

Use line-range fallback only when:
- the needed context is not represented as a symbol
- the symbol range is incomplete
- imports or surrounding type declarations are required
- tests are organized in non-symbol blocks
- documentation sections must be edited
- CLI option parsing is spread across the file
- semantic evidence references point to surrounding source that is not represented as a symbol

Do not retrieve from line 1 to the end unless the whole small file is directly relevant.

Step 9: Data-model inspection, when relevant

Use this only when the task involves data entities, fields, model extraction, or model-to-view lineage.

Generate or refresh data-model artifacts if the current index command does not already generate them:

node dist/cli.js data-model --index <index-dir> --out <index-dir> --json

Inspect an entity:

node dist/cli.js data-model --index <index-dir> --entity "<entity-name>" --json

Inspect a field:

node dist/cli.js data-model --index <index-dir> --field "<entity.field>" --json

Trace model-to-view lineage, when implemented:

node dist/cli.js data-model --index <index-dir> --trace-view "<entity-name>" --json

Trace field-level model-to-view lineage, when implemented:

node dist/cli.js data-model --index <index-dir> --field "<entity.field>" --trace-view --json

Data-model command flags, when implemented:
- --index <dir>: index artifact directory
- --out <dir>: output artifact directory for generated semantic artifacts
- --entity <name>: inspect a data-model entity
- --field <entity.field>: inspect a specific field
- --trace-view <entity>: trace model-to-view usage for an entity
- --json: print machine-readable result

Do not use data-model as a replacement for search, lookup, slice, or source. Use it as focused semantic inspection.

Step 10: Optional graph view

View the code graph (default):

node dist/cli.js view --index <index-dir> --format dot --out <index-dir>/graph.dot --edge-style semantic --json

node dist/cli.js view --index <index-dir> --format svg --out <index-dir>/graph.svg --edge-style semantic --json

View the data-model graph (requires data-model.json in index):

node dist/cli.js view --index <index-dir> --graph data-model --format dot --out <index-dir>/data-model-graph.dot --json

node dist/cli.js view --index <index-dir> --graph data-model --format svg --out <index-dir>/data-model-graph.svg --allow-dot-fallback --json

View the model-view-lineage graph (requires model-view-lineage.json in index):

node dist/cli.js view --index <index-dir> --graph model-view-lineage --format dot --out <index-dir>/lineage-graph.dot --json

node dist/cli.js view --index <index-dir> --graph model-view-lineage --format svg --out <index-dir>/lineage-graph.svg --allow-dot-fallback --json

Fallback when Graphviz is unavailable:

node dist/cli.js view --index <index-dir> --format svg --out <index-dir>/graph.svg --edge-style semantic --allow-dot-fallback --json

View command flags:
- --index <dir>: index artifact directory
- --graph <code|data-model|model-view-lineage>: graph artifact to render (default: code)
- --format <dot|svg|png>: output format
- --out <path>: output file
- --edge-style <semantic|labeled|minimal>: edge visualization mode
- --allow-dot-fallback: write DOT if SVG/PNG rendering cannot run
- --json: print machine-readable result

Edge style modes:
- semantic: styled edges plus legend
- labeled: inline edge labels
- minimal: simple unlabeled edges

Visualization note:
- view --graph data-model renders data-model-graph.json as a DOT/SVG/PNG graph.
- view --graph model-view-lineage renders model-view-lineage.json when it is present in the index.
- Both graph modes fall back to DOT when Graphviz is unavailable and --allow-dot-fallback is set.

Reporting requirements for coding agents

In the final summary, include:

Index artifacts used:
- <index-dir>
- whether the index was refreshed or reused
- whether manifest.json referenced semantic artifacts

Search queries run:
- <query>
- why it was used

Candidate nodes selected:
- <node-id>
- why it was selected

Source symbols retrieved:
- <symbol-node-id>
- why it was retrieved

Line-range fallback retrieval used:
- <file path>
- <line range>
- why symbol-level retrieval was insufficient

Full files read beyond retrieved source:
- <file path>
- why it was necessary
- what missing context it provided

Semantic artifacts inspected:
- <artifact or command>
- why it was relevant

If none were used, say:
- Line-range fallback retrieval used: none
- Full files read beyond retrieved source: none
- Semantic artifacts inspected: none

Architecture guardrail

Before creating new files, identify the existing extension point.

Ask:
- What subsystem already owns this behavior?
- Is there a registry, adapter, command handler, renderer, builder, analyzer, or shared type to extend?
- Would a new file create a second parallel architecture?
- Can this be implemented by extending the existing abstraction instead?
- Does this belong in structural artifacts, compact semantic metadata, or detailed semantic artifacts?

Do not create a new module for a feature until you prove there is no existing extension point.
